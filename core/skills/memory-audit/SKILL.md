# メモリの精査

メモリに書いたファイル・コマンド・設定・前提が今も正しいかを確かめ、古いメモリを信じて間違えることを防ぐ。

利用者の環境だけの決まり（呼び名・追加の確かめる範囲・知識の記録の道具など）は、上書きファイル `${XDG_CONFIG_HOME:-~/.config}/claude-skills/memory-audit.local.md` に書く。あれば最初に読み、本文と食い違う箇所は上書きファイルに従う。

## 0. 範囲

| 操作 | 可否 |
| --- | --- |
| メモリの各ファイルと `MEMORY.md` を直す | 可 |
| 重なったメモリを1つにまとめる（片方へ内容を移し、もう片方は残す） | 可 |
| メモリのファイルを削除する | **不可**。自動のときは削除の候補を `deletions.tsv` に書き、`run.sh` が承認の要否に従って削除するか、削除の承認待ちにする |
| CLAUDE.md・スキル・設定ファイル・リポジトリのファイルを直す | 不可 |
| AWS・ネットワーク・本番環境に問い合わせて確かめる | **不可**。手元のファイルとコマンドの有無だけで確かめる |
| 下の「確かめる範囲」の外を読む | **不可** |

確かめる範囲は次の場所の下に限る: 各設定ディレクトリ（既定は `~/.claude`。2つ目の設定ディレクトリがあれば、それも含む）、`~/.agents`、`~/claude-reports`、`~/.local/state/claude-reports`。
メモリが範囲の外（各リポジトリ、クラウドストレージ等の同期フォルダ、`~/Documents` など）を指していても、確かめに行かない。結果の「確かめられなかったもの」に、理由を「対象外の場所」として書く。
範囲を絞るのは、同期フォルダ等を検索すると macOS がアクセス許可のダイアログを出すためである。自動のときは `run.sh` が Read・Glob・Grep をこの範囲に限り、`ls`・`grep` 等の Bash を許可しない。

自動のときは、上の「不可」を `scripts/run.sh` が権限の設定で強制する。拒否された操作を別の方法で行おうとしてはならない。
直す前の全メモリは、`run.sh` が `~/claude-reports/memory-audit/.snapshots/<日時>/` へ複製してから起動する。

**自動のときは、メモリを直接直さない。** `claude -p` では `~/.claude` 配下が守られたファイルとして扱われ、書き込めないためである。
直した版は、依頼文に書かれた書き込み先（`.staging/<日時>/` の下）へ書く。書き込み先は元の絶対パスの構造を保つが、`.claude` で始まる要素だけは先頭のドットを外してある（例: `<HOME>/.claude/projects/x/memory` → `.staging/<日時>/<HOME>/claude/projects/x/memory`）。ドットを残すと守られたファイルとして書き込みが拒否されるためである。元の位置と書き込み先の対応は依頼文に一覧で書いてある。
元の場所への書き戻しと削除は `run.sh` が行う。書き戻すのは、対象のメモリのディレクトリの直下に同名のファイルが既にある `.md` だけである。新しいファイルは作られない。

### 0.1 承認なしで反映するものと承認待ちにするもの

自動の精査は、見つけた変更（追加・修正・削除・統合）ごとに承認が要るかを自分で判断する。承認が要らないものは承認なしで反映し、要るものは Skill `change-review` の承認待ちに回す（2026-10-16 に利用者の指示で、修正と削除を一律に承認待ちとする扱いから切り替えた）。
ただし、承認の進め方が承認あり（`jobs.conf` の `CLAUDE_REVIEW_APPROVAL_MODE=screen`。既定）のときは、`run.sh` が修正と削除をすべて承認待ちにし、追加だけを反映する（Skill `change-review` の「0.2」）。

承認待ちに回すのは、次のどれかに当たる変更である（Skill `change-review` の「0.1」）。

- 安全のための規則をゆるめる変更（`security-rules`・`commit-guard` の規則、permissions.deny・gitleaks・秘密の検査に関わる記述を消す・変える変更）
- 否認リストに載っている変更（そもそも作らない）、訂正リストで同じ種類が2回訂正された種類の変更
- 消える記述を CLAUDE.md などの移し先へ書き足す必要がある変更
- Claude Code の安全チェックに止められた変更
- 判断に迷うもの

| 変更 | 扱い |
| --- | --- |
| 承認が要ると判断した変更 | 書き込み先の直下の `needs-approval.tsv` に「元の絶対パス<TAB>理由」の形で1行1件書く。直した版は書き込み先へ書いてよい（`run.sh` が書き戻さずに承認待ちにする） |
| 承認が要らない修正・追加（統合でまとめ先へ移した内容を含む） | `run.sh` が書き戻す |
| 承認が要らない削除（統合でまとめられたほうを含む） | `deletions.tsv` に書く。`run.sh` がファイルを消し、そのメモリを指す索引（`MEMORY.md`）の行も消す |
| 承認が要る修正 | `run.sh` が書き戻さず、1ファイル1件の承認待ち（`source: memory-audit`、差分の見出しは元の絶対パス）を `~/claude-reports/proposals/` に作る |
| 承認が要る削除 | `deletions.tsv` と `needs-approval.tsv` の両方に書く。`run.sh` が削除の差分の承認待ちを作る。ファイルは消さない |
| 削除の候補を指す索引（`MEMORY.md`）の行 | claude は消さない。`run.sh` が、削除を反映するときに消すか、そのメモリの削除の案に索引の行の削除を含める。索引だけの案は作らない |

`run.sh` は、`needs-approval.tsv` に挙がっていない変更でも、次のものは承認待ちにする: 訂正リストで同じ種類（`memory-audit/<追加|修正|削除>/<プロジェクト>/<ファイル名>`）が2回訂正されているもの、差分の `-` 行が安全のための規則の語（permissions.deny・gitleaks・秘密の検査・security-rules・commit-guard）を含むもの、行き先の表に移し先への書き足し（`moves.tsv`）か「（候補なし）」があるもの。

承認なしで反映した変更は、`memory-audit-<日時>-<連番>` の ID・種類・直す前の版（`.snapshots/<日時>/` の下の元の絶対パス）とともに、レポートの「承認なしで反映した変更と承認待ち」に載る。あわせて `run.sh` が、直す前と直した後の版を変更の台帳（Skill `change-review` の「9.」。既定 `~/.local/state/claude-change-ledger`）にコミットする。削除と索引の行の削除は同じ ID で記録する。戻すときは `change-review` の `scripts/revert.sh <ID>` を使い、誤りだった場合は「8. 訂正」の手順で訂正リストに足す。

自動のときの `claude -p` には、メモリの書き込み先・レポート以外への書き込みを許していない。加えて、安全のための規則のスキル・フックと定期実行のスクリプト・各設定ディレクトリの CLAUDE.md と settings.json・変更の台帳は、リンクの表記と実体のパスの両方で書き換えを拒否する（南京錠。`change-review` の `link-scopes.sh` の `guard_deny_rules`）。`--permission-mode default` を付け、settings.json の既定の許可の設定で編集が通らないようにする。

- **修正と削除の候補ごとに、消える記述の行き先の表を作る**（Skill `change-review` の「2.2」）。書き込み先の下の `destinations/<候補の元の位置を写した場所>/` に `table.md`（表）を書き、行き先が「記載なし」の記述は、移し先へ書き足した後の全文と `moves.tsv`（「移し先の絶対パス<TAB>ファイル名」）を同じフォルダに置く。書き方の詳細は `run.sh` が依頼文に入れる。
  - 「記載あり」は、行き先のファイルを実際に読み、該当の行を確かめたときだけ書く。行番号を必ず書く。
  - 移し先の候補が無ければ、場所に「（候補なし）」と書く。案の見出しに「（移し先の確認が必要）」が付く。
  - 移し先への追加は、`run.sh` が案の差分に入れるだけで、自動では反映しない（追加だが、削除と一体の変更のため）。移し先への書き足しがある変更は承認待ちになる。
- 承認待ちは `run.sh` がシェルで作る。claude は承認待ちの置き場所へ書かない（権限で拒否している）。
- 依頼文に書かれた否認リスト（`~/claude-reports/proposals/rejections.md`）と訂正リスト（同じ場所の `corrections.md`）を始める前に読む。**否認リストと同じ対象・同じ趣旨の修正・削除は作らない。訂正リストに載った変更は再び行わず、「正しくは」の列を前提にする。**
- 承認待ちの反映は、利用者が会話で「承認分を反映して」「反映して」と言ったときに `change-review` の手順で行う。承認は案の差分の全体（移し先への追加・索引の行の削除を含む）への承認であり、そのまま反映する。

対象は `scripts/targets.conf` のとおり、各設定ディレクトリの全プロジェクトのメモリである。

### 0.2 作成したリポジトリの記録（任意）

各メモリの frontmatter の `metadata` に、そのメモリを作ったときのリポジトリを `repo:`（リポジトリ名。リポジトリの外なら `なし`）と `repo_path:`（パス）で記録できる。
記録は PostToolUse フック（`scripts/tag-memory-repo.sh`）が新しく書いたメモリに足す。既にある値は書き換えない。既存のメモリは `scripts/backfill-memory-repo.sh --apply` で埋め戻せる。フックは `install.sh` では登録しない。使う場合は利用者が settings.json に登録する。
フックを登録している環境では、精査で `repo:` の無いメモリを探し、見つかれば結果の「直したもの」に `backfill-memory-repo.sh` の実行が必要と書く。`repo:` の値そのものは直さない。

## 1. 手順（自動モード）

1. 上書きファイルがあれば読む。続けて、依頼文に書かれた否認リストと訂正リストを読み、対象のメモリを全部読む。
2. 各メモリについて、次を確かめる。
   - 書いてあるファイル・ディレクトリ・スクリプトが実在するか（Read と、find・grep 等の読み取りのコマンド。「0. 範囲」の確かめる範囲の中だけ）。
   - 書いてあるコマンドが手元にあるか（`which`）。
   - 書いてあるリポジトリのブランチは確かめない。リポジトリは確かめる範囲の外であり、「対象外の場所」として書く。
   - 同じ事実を書いた別のメモリが無いか。食い違っていないか。
   - CLAUDE.md・スキル・知識の記録の道具に移った内容を、メモリにも残していないか（メモリの決まり「repo や CLAUDE.md が記録しているものは保存しない」）。
3. 直す（自動のときは、直した版を書き込み先へ書く）。
   - 実物と違う記述は、確かめた事実に直し、末尾に「（2026-xx-xx の精査で修正。旧: …）」と書く。
   - 実物を確かめられない記述（AWS の資源など）は直さない。結果に「確かめられなかったもの」として書く。
   - 重なったメモリは、新しい・詳しいほうへ内容をまとめる。まとめられたほうは削除の候補にし、自動のときは `deletions.tsv` に書く。まとめ先も既存のファイルに限る。
   - 否認リストにある対象・趣旨と同じ修正・削除は作らない。訂正リストで訂正された変更も作らない。
   - `MEMORY.md` の索引が、実在するファイルと一致するよう直す。
   - 変更ごとに承認が要るかを「0.1」で判断し、要るものを `needs-approval.tsv` に書く。
4. 結果を、依頼文に書かれた出力先へ書く。構成は「2.」のとおり。

## 2. 結果の構成

1. 作成日時と、対象のメモリの数
2. 直したもの（ファイル・何をどう直したか・根拠・承認が要ると判断したか）
3. 削除の候補（ファイル・理由。まとめ先があれば書く。承認が要ると判断したか）
4. 確かめられなかったもの（ファイル・記述・確かめられなかった理由）
5. 承認なしで反映した変更と承認待ち（`run.sh` が末尾に足す。「承認なしで反映した変更 N件 / 承認待ちにした N件（番号）」と、反映した変更ごとの ID・種類・直す前の版）
6. 書き戻さなかったファイルと変更の差分（`run.sh` が末尾に足す。自分では書かない）

結果は業務文書として書く。口調・絵文字を使わない。

## 3. 結果を読む依頼への対応

1. Skill `report-inbox` の手順で結果を開き、「承認なしで反映した変更と承認待ち」と「確かめられなかったもの」を中心に伝える。
2. 承認待ちにした変更は、Skill `change-review` の手順で扱う。承認ありの設定では、利用者は画面（既定 `http://127.0.0.1:8010/`）でも承認・保留・却下できる。承認なしの設定では会話で承認する。
3. 承認なしで反映した変更が誤りと分かったら、Skill `change-review` の「8. 訂正」の手順で、利用者に確かめずに直し、訂正リストに1行足す。元に戻すときは、`change-review` の `scripts/revert.sh <ID>` で変更の台帳から戻す（台帳に記録の無い古い変更は `.snapshots/` の複製から戻す）。
