# メモリの精査

メモリに書いたファイル・コマンド・設定・前提が今も正しいかを確かめ、古いメモリを信じて間違えることを防ぐ。

利用者の環境だけの決まり（呼び名・追加の確かめる範囲・知識の記録の道具など）は、上書きファイル `${XDG_CONFIG_HOME:-~/.config}/claude-skills/memory-audit.local.md` に書く。あれば最初に読み、本文と食い違う箇所は上書きファイルに従う。

## 0. 範囲

| 操作 | 可否 |
| --- | --- |
| メモリの各ファイルと `MEMORY.md` を直す | 会話でも自動でも、Skill `change-review` の記録へ足す。自動では作業用の複製だけを直す |
| 重なったメモリを1つにまとめる | 自動では統合の差分を作り、記録へ足す |
| メモリのファイルを削除する | **不可**。自動では候補を`deletions.tsv`へ書き、シェルが削除の差分を記録へ足す |
| CLAUDE.md・スキル・設定ファイル・リポジトリのファイルを直す | 不可 |
| AWS・ネットワーク・本番環境に問い合わせて確かめる | **不可**。手元のファイルとコマンドの有無だけで確かめる |
| 下の「確かめる範囲」の外を読む | **不可** |

確かめる範囲は次の場所の下に限る: 各設定ディレクトリ（既定は `~/.claude`。2つ目の設定ディレクトリがあれば、それも含む）、`~/.agents`、`~/claude-reports`、`~/.local/state/claude-reports`。
メモリが範囲の外（各リポジトリ、クラウドストレージ等の同期フォルダ、`~/Documents` など）を指していても、確かめに行かない。結果の「確かめられなかったもの」に、理由を「対象外の場所」として書く。
範囲を絞るのは、同期フォルダ等を検索すると macOS がアクセス許可のダイアログを出すためである。自動のときは `run.sh` が Read・Glob・Grep をこの範囲に限り、`ls`・`grep` 等の Bash を許可しない。

自動のときは、上の「不可」を `scripts/run.sh` が権限の設定で強制する。拒否された操作を別の方法で行おうとしてはならない。
直す前の全メモリは、`run.sh` が `~/claude-reports/memory-audit/.snapshots/<日時>/` へ複製してから起動する。

**自動のときは、メモリを直接直さない。** `claude -p` では `~/.claude` 配下が守られたファイルとして扱われ、書き込めないためである。
直した版は、依頼文に書かれた書き込み先（`.staging/<日時>/` の下）へ書く。書き込み先は元の絶対パスの構造を保つが、`.claude` で始まる要素だけは先頭のドットを外してある（例: `<HOME>/.claude/projects/x/memory` → `.staging/<日時>/<HOME>/claude/projects/x/memory`）。ドットを残すと守られたファイルとして書き込みが拒否されるためである。元の位置と書き込み先の対応は依頼文に一覧で書いてある。
元の場所へは書き戻さず、ファイルも削除しない。
`run.sh`が作業用の版と起動前の複製を比べ、追加・修正・削除・統合を記録に足す。

### 0.1 自動のときの変更の記録

記録の場所は`~/.local/state/claude-reports/changes/log.md`とする。
`CLAUDE_REVIEW_CHANGES_LOG`で差し替えられる。
追記は`run.sh`がシェルから行い、`claude -p`は記録を直接編集しない。

| 変更 | Claudeが書くもの | シェルが行うこと |
| --- | --- | --- |
| 追加・修正 | 作業用のフォルダに直した版を書く | 追加は`new-change.sh`、修正は`propose.sh`で記録へ足す |
| 削除 | `deletions.tsv`へ「元の絶対パス<TAB>理由」を書く | ファイルと索引の行の削除を1件の差分にする |
| 統合 | まとめ先の版と、まとめられる側の削除の候補を書く | 移し先への追加・削除・索引の変更を1件にまとめる |
| 要確認と判断した変更 | `needs-approval.tsv`へ「元の絶対パス<TAB>理由」を書く | 区分を`要確認`にする |

区分の判断はSkill `change-review`の「0.1」に従う。
同じ種類が2回訂正された変更、安全のための規則を変える変更、行き先の表の欠けもシェルが`要確認`にする。
種類は`memory-audit/<追加|修正|削除>/<プロジェクト>/<ファイル名>`とする。

修正・削除の候補ごとに、消える記述の行き先の表を作る（Skill `change-review`の「2.2」）。
作業用の`destinations/<候補の元の位置を写した場所>/`へ`table.md`を書く。
移し先へ書き足す場合は、書き足した後の全文と`moves.tsv`も同じ場所に置く。
「記載あり」は実物の行番号を確かめてから書く。
候補が無ければ`（候補なし）`と書く。
移し先を直接編集しない。

自動のClaudeには、作業用のフォルダと結果以外への書き込みを許可しない。
安全のための規則のスキル・フック・定期実行のスクリプト・設定・過去の台帳・変更の記録は書き換えを拒否する。
リンクは表記と実体の両方を守る（`link-scopes.sh`の`guard_deny_rules`）。
`--permission-mode default`を使う。
否認リストと訂正リストを始める前に読む。
否認された変更と、訂正リストの「正しくは」に反する変更は作らない。
会話のClaudeが記録を読み、Skill `change-review`の手順で入れる。

### 0.2 作成したリポジトリの記録（任意）

各メモリの frontmatter の `metadata` に、そのメモリを作ったときのリポジトリを `repo:`（リポジトリ名。リポジトリの外なら `なし`）と `repo_path:`（パス）で記録できる。
記録は PostToolUse フック（`scripts/tag-memory-repo.sh`）が新しく書いたメモリに足す。既にある値は書き換えない。既存のメモリは `scripts/backfill-memory-repo.sh --apply` で埋め戻せる。フックは `install.sh` では登録しない。使う場合は利用者が settings.json に登録する。
フックを登録している環境では、精査で `repo:` の無いメモリを探し、見つかれば結果の「直したいもの」に `backfill-memory-repo.sh` の実行が必要と書く。`repo:` の値そのものは直さない。

## 1. 手順（自動モード）

1. 上書きファイルがあれば読む。続けて、依頼文に書かれた否認リストと訂正リストを読み、対象のメモリを全部読む。
2. 各メモリについて、次を確かめる。
   - 書いてあるファイル・ディレクトリ・スクリプトが実在するか（Read と、find・grep 等の読み取りのコマンド。「0. 範囲」の確かめる範囲の中だけ）。
   - 書いてあるコマンドが手元にあるか（`which`）。
   - 書いてあるリポジトリのブランチは確かめない。リポジトリは確かめる範囲の外であり、「対象外の場所」として書く。
   - 同じ事実を書いた別のメモリが無いか。食い違っていないか。
   - CLAUDE.md・スキル・知識の記録の道具に移った内容を、メモリにも残していないか（メモリの決まり「repo や CLAUDE.md が記録しているものは保存しない」）。
3. 直した版を書き込み先へ書く。元のファイルは直さない。
   - 実物と違う記述は、確かめた事実に直し、末尾に「（2026-xx-xx の精査で修正。旧: …）」と書く。
   - 実物を確かめられない記述（AWS の資源など）は直さない。結果に「確かめられなかったもの」として書く。
   - 重なったメモリは、新しい・詳しいほうへ内容をまとめる。まとめられたほうは削除の候補にし、自動のときは `deletions.tsv` に書く。まとめ先への変更と削除を同じ記録にまとめる。
   - 否認リストにある対象・趣旨と同じ修正・削除は作らない。訂正リストで訂正された変更も作らない。
   - `MEMORY.md` の索引が、実在するファイルと一致するよう直す。
   - 変更ごとに承認が要るかを「0.1」で判断し、要るものを `needs-approval.tsv` に書く。
4. 結果を、依頼文に書かれた出力先へ書く。構成は「2.」のとおり。

## 2. 結果の構成

1. 作成日時と、対象のメモリの数
2. 直したいもの（ファイル・何をどう直すか・根拠・区分の判断）
3. 削除の候補（ファイル・理由。まとめ先があれば書く。承認が要ると判断したか）
4. 確かめられなかったもの（ファイル・記述・確かめられなかった理由）
5. 記録に足した直したいこと（`run.sh`が末尾に足す。ID・区分・対象・要約）
6. 記録しなかった候補と変更の差分（`run.sh`が末尾に足す）

結果は業務文書として書く。口調・絵文字を使わない。

## 3. 結果を読む依頼への対応

1. Skill `report-inbox`の手順で結果を開く。「記録に足した直したいこと」と「確かめられなかったもの」を中心に伝える。
2. 記録（`~/.local/state/claude-reports/changes/log.md`）の未対応の項目は、`直してよい`は会話で入れ、`要確認`は利用者の承認を受けてから入れる。
3. 入れた変更の誤りは、正しい内容へ直し、訂正リストに残す。元に戻す場合は会話で残したbackupを使う。過去のIDは`revert.sh`か`.snapshots/`の複製から戻す。
