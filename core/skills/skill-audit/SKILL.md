# スキルの精査

スキル同士の規則がぶつかり、直す範囲が広がることを防ぐために、スキル群を定期的に精査する。
精査の目的は、**規則を用途ごとに分け、1つの規則を1か所にだけ書くことで、修正の影響範囲を絞ること**である。

利用者の環境だけの決まり（区分の具体名・分割の現況・既知の注意・CLAUDE.md の節名など）は、上書きファイル `${XDG_CONFIG_HOME:-~/.config}/claude-skills/skill-audit.local.md` に書く。あれば最初に読み、本文と食い違う箇所は上書きファイルに従う。

## 0. 対象範囲（厳守）

スキルの置き場所（以下 ROOT）は、環境変数 `SKILL_AUDIT_ROOT`（既定 `~/.claude/skills`）である。2つ目の設定ディレクトリを使い、その `skills` が ROOT へのリンクになっている場合は、どちらも同じ場所を指す。
スキルの一覧と本文は、承認ありの設定では承認の画面（既定 `http://127.0.0.1:8010/skills`）の「スキル」の欄で閲覧できる（閲覧のみ）。

| 区分 | 該当 | 読む | 直す | 削除する |
| --- | --- | --- | --- | --- |
| 自作のスキル | ROOT 直下のディレクトリのうち、下の行に当たらないもの（`skill-audit` 自身を含む）。ROOT 直下のリンクのうち、実体が `SKILL_AUDIT_OWN_LINK_ROOTS`（既定は本リポジトリの `core/skills`）の下にあるもの | 可 | 可 | 可（`skill-audit` 自身とリンクは不可） |
| 導入した外部のスキル | 手動で複製したもの、`npx skills` 等が張ったリンク（実体は `~/.agents/skills/` 等） | 可 | **不可**。上書きの必要な規則は自作のスキル（調停用のスキル）に書く | 可 |
| 別リポジトリにあるスキル | 実体が別のリポジトリにあるリンク | 可 | **不可**。会話の中で利用者に頼まれたときだけ直す | 不可 |
| リポジトリ内のスキル | 各リポジトリの `.claude/skills/`（Git 管理外のことがある） | 可 | 会話の中で利用者に頼まれたときだけ直す。自動の精査では直さない | 会話の中で利用者に頼まれたときだけ。ゴミ箱（`~/.Trash/`）へ移す |
| プラグインのスキル | `~/.claude/plugins/` 配下 | 可 | 不可 | 不可 |
| 対象外 | `SKILL_AUDIT_EXCLUDE`（空白区切り）に挙げた名前（同期やプラグインの置き場所）、`.` で始まるディレクトリ、Claude Code 組み込みのスキル | 不可 | 不可 | 不可 |
| CLAUDE.md | 各設定ディレクトリの `CLAUDE.md` | 可 | 会話の中の精査では、利用者の決まりで許されていれば可。安全のための規則の節は不可。**自動の精査では不可**（権限で拒否している） | 不可 |
| 対象外 | 各 `settings.json` | 可（参照関係の確認のため） | **不可** | 不可 |

- 上の表の「不可」は、精査の結果どれだけ良くなる場合でも破らない。
- 具体的にどのスキルがどの区分に当たるかは、上書きファイルに書く。
- 自動の精査で CLAUDE.md の変更が必要だと判断した場合は、直さずに `history.md` の「未決事項」へ書き、次の会話の中で直す。
- 新しいスキルや外部のスキルが増えたら、どの区分に当たるかを判定し、上書きファイルの表を直してから精査する。判定できない場合は対象外として扱う。

## 1. 実行の形

| 形 | 呼ばれ方 | 報告 |
| --- | --- | --- |
| 依頼 | 利用者が「スキルを精査して」等と頼む | 変更の要約を会話で返す |
| 変更後 | スキルの追加・修正・削除の作業の最後 | 変更があれば要約を会話で返す |
| 指示の反映 | 利用者が出力の方向性を直し、スキルへ書き込んだ後 | 書き込んだ内容を1行で返す |
| 自動 | 週1回 `launchd` が `scripts/run-audit.sh` を起動する（macOS のみ。止めるときは `launchctl bootout gui/$(id -u)/<ラベル>`。ラベルは `~/.local/state/claude-review-inbox/scheduled-jobs.tsv` で確かめる）。前回から対象のファイルが変わっていない週は起動しない。変更ごとに承認が要るかを判断し、要らないものは反映し、要るものは承認待ちにする（「1.1」） | 会話では報告しない。`history.md` と結果（`~/claude-reports/skill-audit/`）に残す |

変更後の精査は、変更したスキルと、それを参照している・それが参照しているスキルに範囲を絞ってよい。

自動のときは、「0. 対象範囲」の「直す」「削除する」の不可を、`run-audit.sh` が `claude` の権限の設定（`--allowedTools` / `--disallowedTools`）で強制する。
許可されているのは、ROOT 配下の編集（対象外のディレクトリは拒否）、承認が要る変更の一覧（`needs-approval.tsv`）と行き先の表の書き込み、`snapshot.sh` と `trash-skill.sh`、`date`、範囲を限った読み取りだけである。
ROOT 配下と自作のスキルの実体の中でも、安全のための規則のスキル（`SKILL_AUDIT_PROTECTED`）全体、フックと定期実行のスクリプト（既定は `security-rules`・`memory-audit`・`report-inbox`・`repo-patrol`・`secret-patrol`・`skill-audit`・`feedback-mining`・`change-review` の各 `scripts/`。`jobs.conf` の `CLAUDE_REVIEW_GUARDED_PATHS` で変えられる）、各設定ディレクトリの CLAUDE.md・settings.json・settings.local.json、変更の台帳は、リンクの表記と実体のパスの両方で書き換えを拒否する（南京錠。Skill `change-review` の `link-scopes.sh` の `guard_deny_rules`）。自動のときは `--permission-mode default` を付け、settings.json の既定の許可の設定（acceptEdits 等）で作業場所の中の編集が通らないようにする。
`snapshot.sh` と `trash-skill.sh` は、ROOT の `skill-audit/scripts/` の下の絶対パス（`~` を展開した形）で呼ぶ。自動のときは `run-audit.sh` が依頼文でそのパスを渡すため、そのとおりに呼ぶ。相対パスや別の表記で呼ばない。Bash の許可は文字列の前方一致で判定されるため、別の表記で呼ぶと許可待ちで止まる。
読み取りは Read と、find・grep 等の読み取りのコマンドで、各設定ディレクトリ・`~/.agents`・`~/claude-reports`・`~/.local/state/claude-reports`・ROOT・変更の記録と複製（「3.」）と、スキルの置き場所の直下にあるリンクの実体の下に限る。書き込みは ROOT と、変更の記録（`history.md`）に限る。`ls`・`grep`・`stat` 等の Bash は許可していない。同期フォルダ等を検索すると macOS がアクセス許可のダイアログを出すためである。
権限で拒否された操作を、別の方法で行おうとしてはならない。仕組みの詳細は `scripts/README.md` にある。

### 1.1 自動のときの承認の要否

自動の精査は、行う変更（追加・修正・削除・統合）ごとに承認が要るかを自分で判断する。承認が要らないものはそのまま残り、要るものは Skill `change-review` の承認待ちになる（2026-10-16 に利用者の指示で、修正と削除を一律に承認待ちとする扱いから切り替えた）。
ただし、承認の進め方が承認あり（`jobs.conf` の `CLAUDE_REVIEW_APPROVAL_MODE=screen`。既定）のときは、`run-audit.sh` が修正と削除をすべて承認待ちにし、追加だけを残す（Skill `change-review` の「0.2」）。

承認待ちに回すのは、次のどれかに当たる変更である（Skill `change-review` の「0.1」）。

- 安全のための規則をゆるめる変更（`security-rules`・`commit-guard` の規則をゆるめる・消す変更、permissions.deny・gitleaks・秘密の検査に関わる記述を消す・変える変更）
- 否認リストに載っている変更（そもそも行わない）、訂正リストで同じ種類が2回訂正された種類の変更
- 消える記述を CLAUDE.md などの移し先へ書き足す必要がある変更
- Claude Code の安全チェックに止められた変更
- 判断に迷うもの

承認が要ると判断した変更は、行ったうえで、依頼文に書かれた `needs-approval.tsv`（`runs/<日時>/` の下）に「対象の絶対パス<TAB>理由」の形で1行1件書く。ファイルの修正・削除はファイルの、スキルの削除はスキルのディレクトリの絶対パスを書く（スキルのディレクトリを書くと、そのスキルの中の変更がすべて承認待ちになる）。

| 変更 | `run-audit.sh` の扱い |
| --- | --- |
| 承認が要らない変更（追加・修正・ファイルの削除） | 残す。直す前の版を `history/<日付>/<スキル名>__<相対パスの / を _ にした名前>.bak` に複製し（既にあれば最初の版を残す）、ID を振って `history.md` と結果に載せる |
| 承認が要らないスキルの削除（`trash-skill.sh`） | 退避先（`.skill-audit-trash/`）に残す。直す前の版を `history/<日付>/<スキル名>__skill/` にも複製する。そのスキルを参照する他の箇所の修正も残す |
| 新しいファイル、新しいスキル | 残す。ID を振って記録する |
| 承認が要る修正 | ファイルを実行前の版に戻し、その差分を1ファイル1件の承認待ちにする |
| 承認が要るファイルの削除 | 実行前の版に戻し、削除の差分を承認待ちにする |
| 承認が要るスキルの削除 | `.skill-audit-trash/` から元の場所へ戻し、スキルの全ファイルの削除の差分を1件の承認待ちにする。そのスキルを参照する他の箇所の修正（差分の `-` 行がスキルの名前を含むもの）も、別の案にせず同じ案に入れる。承認されると差分のとおり全ファイルを消し、空になったフォルダも消す |

- `run-audit.sh` は、`needs-approval.tsv` に挙がっていない変更でも、次のものは承認待ちにする: 訂正リストで同じ種類（`skill-audit/<追加|修正|削除>/<スキル名>`）が2回訂正されているもの、安全のための規則のスキル（環境変数 `SKILL_AUDIT_PROTECTED`、既定 `security-rules commit-guard`）の修正・削除、差分の `-` 行が permissions.deny・gitleaks・秘密の検査を含むもの、行き先の表に移し先への書き足し（`moves.tsv`）か「（候補なし）」があるもの。
- 承認なしで反映した変更の ID は `skill-audit-<実行の日時>-<連番2桁>` である。`history.md` の記録と、結果 `~/claude-reports/skill-audit/<日付>.md` の「承認なしで反映した変更と承認待ち」の節に、ID・種類・直す前の版のパスを載せる。結果は Skill `report-inbox` の未読の知らせに出る。あわせて、直す前と直した後の版を変更の台帳（Skill `change-review` の「9.」。既定 `~/.local/state/claude-change-ledger`）にコミットする。戻すときは `change-review` の `scripts/revert.sh <ID>` を使い、誤りだった場合は「8. 訂正」の手順で訂正リストに足す。
- `run-audit.sh` は起動の前に対象のスキル群を `~/.local/state/skill-audit/runs/<日時>/before/` へ複製し、終わった後に比べる。変更の記録と複製（「3.」）はスキル置き場の外にあるため、比べる対象に入らない。
- **修正・削除ごとに、消える記述の行き先の表を作る**（Skill `change-review` の「2.2」）。`runs/<日時>/destinations/<対象の元の位置を写した場所>/` に `table.md`（表）を書く。スキルの削除では、スキルのディレクトリを対象とする。行き先が「記載なし」の記述は、移し先へ書き足した後の全文と `moves.tsv` を同じフォルダに置き、移し先のファイルは直接直さない（直接直すと実行前の版に戻される）。書き方の詳細は `run-audit.sh` が依頼文に入れる。移し先への追加は案の差分に入るだけで、自動では反映しない。
- 承認待ちは `run-audit.sh` がシェルで作り、`history.md` の先頭へ「承認なしで反映した変更」と「承認待ちにした変更」の番号を書く。claude は承認待ちの置き場所と判断の台帳へ書き込めない（権限で拒否している）。
- 自動の精査は、始める前に否認リスト（`~/claude-reports/proposals/rejections.md`）と訂正リスト（同じ場所の `corrections.md`）を読む（どちらも依頼文にパスがある）。**否認リストと同じ対象・同じ趣旨の修正・削除は行わない。訂正リストに載った変更は再び行わず、「正しくは」の列を前提にする。**
- 承認待ちの反映は、利用者が会話で「承認分を反映して」「反映して」と言ったときに `change-review` の手順で行う。承認は差分の全体への承認であり、スキルの削除の案も差分のとおり反映する（承認ありの設定では画面のボタンでも反映される）。
- 会話の中の精査（依頼・変更後・指示の反映）は承認待ちにしない。

## 2. 手順

### 2.0 否認リストと訂正リスト

否認リスト（`~/claude-reports/proposals/rejections.md`）と訂正リスト（同じ場所の `corrections.md`）を読む。否認リストは利用者が却下した変更、訂正リストは承認なしで反映した変更のうち誤りと分かって直したものの一覧である。
同じ対象・同じ趣旨の修正・削除と、訂正された変更は、会話の中の精査でも行わない。

### 2.1 棚卸し

1. ROOT 直下の一覧を取り、「0. 対象範囲」の区分に振り分ける。
2. スキルごとに、`SKILL.md` の行数・付属ファイルの数・最終更新日を記録する。自動のときは `stat` を使えないため、最終更新日は記録しない。

### 2.2 使用実績

会話の履歴（各設定ディレクトリの `projects/**/*.jsonl`）から数える。

- Skill ツールの呼び出し（`"name":"Skill"` の `input.skill`）と、利用者が打った `/<スキル名>` の両方を数える。
- スキルとして呼ばれずに、付属のスクリプトや `SKILL.md` を直接使っている場合がある。スキルのパスへの参照も検索する。
- 設定ディレクトリが2つあると、同じセッションの複製が両方に残っていることがある。回数は延べ数として扱い、多寡の判断だけに使う。

### 2.3 重複とぶつかり

スキルの本文・`references/`・CLAUDE.md を全文読み、次を洗い出す。抜粋で済ませない。

- **用途**: 1つのスキルの中にある、呼ばれる依頼の種類が異なるまとまり。見出しと行範囲で記録する。
- **重複**: 同じ事項を複数か所に書いている箇所。
- **食い違い**: 同じ事項について内容が一致しない箇所。どこで調停しているかも確かめる。
- **参照切れ**: 他のスキルや CLAUDE.md の節を名前で参照していて、参照先が無い、または名前が変わっている箇所。
- **孤立**: 他と同じ話題を扱うのに、どこも参照していないスキル。食い違いが表に出にくい。

調べる対象が多いときは、独立した調査ごとにサブエージェントへ任せてよい。
サブの報告にある指摘は、直す前に原文で確かめる（同じディレクトリへの2つのリンクを「リンクが2つある」と誤って報告することがある）。

### 2.4 直し方の判断

| 状況 | 直し方 |
| --- | --- |
| 複数のスキルが同じ規則を持つ | 必ず効かせたい規則は、呼ばれるスキルの本文に直接書く（重複を許す）。共通部品のスキルへ一本化して1行で参照するのは、読まれなくても困らない補足だけにする |
| 1つのスキルに、呼ばれる条件が違う用途が混ざる | 用途ごとに別のスキルへ分ける。呼ばれる条件が同じなら分けずに `references/` へ移す |
| 外部のスキルと自作の規則が食い違う | 外部の本体は直さず、調停を自作のスキル（調停用のスキル）に書く |
| 参照切れ | 参照先の現在の名前に直す |
| 孤立したスキル | 同じ話題を扱うスキルへの参照を足す |
| 不要なスキル | 「2.5 削除」の条件を満たせば削除する |

- 「参照で済ませない」根拠: 本文の「Skill X に従う」は、実際の会話ではほとんど辿られない。必ず効かせたい規則を参照先にだけ書くと、効かない。
- 同じ規則を複数のスキルの本文に書いた場合は、精査のたびに突き合わせて食い違いを確かめる。食い違いは新しい方の決定に揃え、どちらが新しいか判断できなければ利用者の判断が要る事項とする。
- 会話の中の精査では、スキル同士の統合（内容を別のスキルへ移す・まとめる）は利用者に確かめずに行い、行った後に1行で伝える。統合の後に元のスキルを消す場合は、「2.5」に従って削除の前に確認する。
- 分けた後は、各スキルの `description` に「何から参照されるか」「何を参照するか」を書く。呼び出しの判断に使われるためである。
- 移した規則には、移した日付と移した元を書く（例:「2026-01-01 に CLAUDE.md から移設」）。
- 利用者の判断が要る事項（どちらの規則を正とするか等）は、会話の中なら利用者に確認する。自動のときは推奨案を採用し、理由を `history.md` に書く。

### 2.5 削除

次の3つを**すべて**満たすスキルだけを削除する。1つでも判断できなければ削除しない。

1. 直近90日の使用実績が無い（スキルとしての呼び出しも、付属ファイルの直接利用も無い）。
2. 作業の対象が終わっている、または同じ規則を持つ別のスキルへ統合済みである。痕跡（git の履歴・課題の状態・統合先の記述）で確かめる。
3. 他のスキルと CLAUDE.md から参照されていない。参照されている場合は、参照を先に直す。

- 削除は `rm` ではなく移動で行う。ROOT の `skill-audit/scripts/trash-skill.sh <スキル名>` を絶対パスで使う（「1」の呼び方）。移動先は `<ROOT>/.skill-audit-trash/<YYYY-MM-DD-HHMMSS>-<スキル名>/` である。
  このスクリプトは対象外のスキル・`skill-audit` 自身・シンボリックリンクを拒否する。
  ROOT 直下の `.trash/` は同期の仕組みが使っていることがあるため、混ぜない。
- 会話の中で精査している場合は、削除の前に利用者に1件ずつ確認する。
- 自動の精査で削除した場合は、承認が要らないと判断したものは退避先に残り、要るものは `run-audit.sh` が元に戻して削除の承認待ちにする（「1.1」）。

### 2.6 変更の記録

1. **直す前に、元のファイルを複製する。** ROOT の `skill-audit/scripts/snapshot.sh <スキル名> <スキル内の相対パス>` を絶対パスで使う（「1」の呼び方）。複製先は `${SKILL_AUDIT_STATE:-$HOME/.local/state/skill-audit}/history/<YYYY-MM-DD>/<スキル名>__<スキル内の相対パスの / を _ に置き換えた名前>.bak` とする。
   同じ日に同じファイルを2回直す場合は、最初の版だけを残す。
2. **直した後に、`${SKILL_AUDIT_STATE:-$HOME/.local/state/skill-audit}/history.md` の先頭へ記録を足す。** 書式は `history.md` の冒頭に従う。
   日付・実行の形・変更したスキルと内容・理由・複製の場所・未決事項を書く。

### 2.7 確認

- 直したスキルの `SKILL.md` に、frontmatter の `name` と `description` があること。
- 参照しているスキル名がすべて実在すること（`<ROOT>/<名前>/SKILL.md` を確かめる）。
- 参照している節の名前が、参照先に実在すること。
- 新しいスキルが、セッションのスキル一覧に出ること（会話の中で精査した場合）。

### 2.8 公開版の点検

スキルを公開版のリポジトリへ書き出している場合に、公開版へ業務の語（社名・個人名・利用者の環境の名前など）が混ざっていないかを調べる。書き出しの時点の検査をすり抜けた語や、後から禁止語に加えた語を見つけるためである。

| 項目 | 内容 |
| --- | --- |
| 何を | 一覧に挙げた公開版のディレクトリを、共通の検査器の `check.sh <ディレクトリ>`（業務の語の自動収集を含む）で調べる。検出と報告だけを行い、公開版のファイルは直さない |
| いつ | 自動の精査のたび（週1回）。`scripts/run-audit.sh` が `scripts/check-public.sh` を呼ぶ。スキルに変更が無く精査を省略する週も行う。`--dry-run` では行わない |
| どこに書くか | 当たり・検査器の失敗・一覧のディレクトリが無い・検査器が無い場合だけ、`~/claude-reports/skill-audit/<YYYY-MM-DD>.md` の「公開版の点検」の節に書く。未読の結果として Skill `report-inbox` の知らせに出る。当たりが無ければ結果を書かない |
| 検査器 | 環境変数 `PUBLIC_CHECK_DIR` に書いたディレクトリの `check.sh`。環境変数が無ければ `${XDG_CONFIG_HOME:-~/.config}/claude-skills/public-check-dir` の1行目（例 `~/path/to/public-check`）から読む。どちらも無い場合は「検査器の場所が設定されていない」と結果に書き、点検を飛ばして精査は続ける。検査器が無い場合も同じく結果に書く |

公開版のディレクトリの一覧は `${XDG_CONFIG_HOME:-~/.config}/claude-skills/public-dirs.txt` に置く（環境変数 `SKILL_AUDIT_PUBLIC_DIRS` で変えられる）。一覧が無ければ点検をしない。

- 1行に1つのディレクトリの絶対パスを書く。先頭の `~` はホームに置き換える。
- `#` で始まる行と空行は使わない。

```text
# 公開版のリポジトリ
~/repos/my-skills-public
~/repos/my-tools-public
```

結果を受け取ったら、当たった語を公開版の元（全部入りのリポジトリ）で直してから、書き出しをやり直す。公開版のディレクトリを直接直さない。

## 3. 変更履歴の見方

変更の記録と複製は、スキル置き場の外の状態の置き場所 `${SKILL_AUDIT_STATE:-$HOME/.local/state/skill-audit}/` に置く。本文で `history.md`・`history/` と書くときは、この下を指す。

- `history.md` — 精査ごとの記録。新しいものが上。
- `history/<日付>/` — 直す前のファイルの複製。今のファイルと `diff` を取れば、その日に何を変えたかが分かる。
- `<ROOT>/.skill-audit-trash/` — 削除したスキル。元の場所へ戻せば復元できる。
- 変更の台帳（既定 `~/.local/state/claude-change-ledger`。Skill `change-review` の「9.」） — 自動の精査が承認なしで反映した変更の、直す前と直した後の版。ID ごとにコミットがある。`change-review` の `scripts/revert.sh <ID>` で戻せる。

## 4. 分割の現況

スキルごとの役割と主な参照元の表は、利用者の環境ごとに異なるため上書きファイルに置く。精査で分割・統合をしたら、上書きファイルの表を直す。

## 5. 既知の注意

- 本 Skill の本文自体も精査の対象である。規則が他のスキルと重なったら、本 Skill の側を参照に置き換える。
- 外部のスキルの注意（類似スキルとの併用の禁止など）を、意図的に破って運用している場合は、上書きファイルにその旨を書く。精査でその注意を理由に削除しない。
